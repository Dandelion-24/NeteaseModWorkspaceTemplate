# 组件架构

先读根 `AGENTS.md`、catalog 与任务涉及的 `COMPONENT.md`。区分正在比较创意、已批准的设计和已有运行工程，按实际阶段工作。

## 稳定约束

- 组件有唯一稳定 ID、事件归属、资源命名空间、私有数据边界和可信服务端入口。显示名称、组件 ID、Python 包名是不同概念；Python 包名须符合解释器标识符规则。
- 客户端负责输入与展示，服务端验证身份、权限、目标与世界修改。共享模块只放真正跨组件的稳定内容，不读取其他组件的私有注册表或 UI 状态。
- 当前路径与状态相互一致；历史结论保留原版本和证据等级。已交付包与只读原件不因目录整理被改写。

## 按任务执行

1. 纯创意阶段只输出方案。正式设计成立后可创建组件说明和 catalog 的 `design` 条目，版本与运行工程为空；实际实现时再创建版本工程并更新状态。不预建无任务的类型树。
2. 明确输入、事件、状态所有者、存储与失败恢复边界。引擎接口先交给 ModSDK 核心核对，不为凑架构预设未经验证的组件组合。
3. 一般位置为 `components/<type>/<component-id>/COMPONENT.md` 与 `mcstudio_project/<ProjectName>_v<version>/`。按复杂度拆模块，不强迫简单功能套一整套抽象层。
4. 在开发版本内按授权修改；发布新版本时使用明确的版本目录和升级边界。纯说明或工具维护不自动升玩法版本。
5. 需要清理时先核对现有授权、完整路径、引用与测试依赖，保存必要证据和最小回归源。未被任务覆盖的历史工程不自动删除。

`COMPONENT.md` 记录入口、请求契约、真实服务端行为、持久化、资产、适用技能和验证资料。存在 UI 时声明页面职责与交互状态，遵循[通用界面质量合同](../netease-visual-assets/references/ui-ux-quality.md)，不由目录架构指定菜单风格或固定页签数量。

## 完成判据

catalog、组件说明和当前工程指针可达，身份/资源/数据归属清晰；清理后现行工具不依赖已删除路径。打包布局与投稿检查按交付技能，不在架构文档复制另一套规则。
