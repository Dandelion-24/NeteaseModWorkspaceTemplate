# 单工程校验

先确定任务组件、目标版本、改动范围和需要的证据。没有运行工程的 `design` 条目只检查设计与登记；纯文案、工具或局部修复不机械重跑无关全矩阵。

## 必查一致性

- catalog 的 ID、状态与路径正确；当前版本、Manifest、依赖、说明和测试资料一致，历史证据不改成当前通过。
- Python 与 JSON 能按各自目标解析。**游戏代码按 Python 2.7 语义校验，不能把 Python 3 AST/compile 的拒绝当成 Python 2 语法错误。** 宿主脚本另检 Python 3；缺目标解释器时报告静态检查局限。
- 导入、常量、跨模块辅助函数和实际实例成员存在；动态关系无法静态证明时列出调用链与待测路径，不靠字符串同名假定可用。
- 对照[接口合同](../netease-modsdk-core/references/api-contract-checklist.md)逐调用检查所属端、owner、签名、事件字段、返回形状、取消对象与失败消费。模拟样例采用真实形状，不用虚构的 `(ok, data)` 让测试自洽。
- 客户端请求、远端系统监听、白名单/类型校验、服务端身份和响应消费闭合。候选目标不等于事实，服务端重验后才能修改世界。
- 新增的交易、回滚、重试和恢复路径检查重复/部分成功/未知结果；必要时做临时副本中的正反样例，不破坏正式包来证明断言。

## UI、资产和包

有 UI 时应用[界面质量合同](../netease-visual-assets/references/ui-ux-quality.md)：控件路径、布局状态、文本/命中区、背景归属、关闭和晚回包都要核对。原生、自绘和继承模板均可；检查实际基类定义、变量作用域与绑定，不能用固定风格、模板名或关键词作为失败判据。

资源检查区分模型、贴图、图标和逻辑引用，核对命名空间、图集、PNG、UV 与资产归属。只有涉及结构放置时才核对结构命名空间、原件哈希、方向和区块范围；原件哈希相同不能证明资源注册或放置语义正确。

Manifest 与所选交付布局按交付技能核验。静态包检查不证明测试世界已启用 BP/RP；用户提供运行环境时再核对实际 UUID/version 激活记录。

## 检查器和结果

优先使用适用的现有工程校验器，必要时补针对本次风险的检查；模板不提供覆盖所有未来组件的万能校验器。跨组件关系交给工作区审计，不重复写一套推断。

用 `PASS`、`WARNING`、`FAIL`、`RUNTIME TEST REQUIRED` 标记结果，附实际依据、影响和相应验证方式。路径问题可由静态修复复核，视觉/输入等才要求游戏手测；不强迫每条警告都跑游戏。投稿前运行 pylint 错误级辅助检查，记录工具版本并识别 Python 2 内建符号等环境差异。
