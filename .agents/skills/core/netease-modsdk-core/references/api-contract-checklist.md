# 接口合同核对表

本表用于新增或改变的 API、事件、JSON 组件和关键组合。它约束依据与语义，不规定必须选哪一种实现。纯文案、同合同内的参数值调整可引用有效记录；签名、目标版本、调用端或生命周期变动时重新核对相关项。

## 查证顺序

1. 在正式 `docs/mcdocs/` 搜索准确名称并打开正文；再查 `mcguide`、`mconline`。确认不是同名 beta、旧版或另一端的接口。
2. 同时读参数、返回值、备注、示例和适用版本。示例不能覆盖正文，索引没有展示的限制仍须读到。
3. 对组合能力逐个核对相互限制。不能从邻近组件的警告推导“不支持”，也不能从“没写不支持”推导“支持”。
4. 资料冲突时记录双方具体段落、目标版本与未决项，再核对当前正式资料或做受控最小验证。无解的关键项保留阻塞范围与替代方案，不制造成功结论。

## 建议记录字段

记录放在组件维护的接口表或工程 `validation/` 中，已有表直接扩充，不为同一接口重复建多份事实源。

| 栏目 | 必须回答的问题 |
| --- | --- |
| 用途与调用位置 | 解决什么问题，源码/JSON 的哪个入口在使用？ |
| 本地依据 | 实际正文路径、标题/锚点或行号、目标档位；必要时保留文档哈希 |
| 所属端与宿主 | 客户端还是服务端，是模块函数还是哪种组件方法，owner 是玩家/实体/level 中哪一个？ |
| 签名与字段 | 参数个数、顺序、类型、可选值、单位、坐标系、维度、大小写；事件是否无参？ |
| 返回形状 | 单值、dict、list、tuple 还是 bool；空值/失败值分别是什么意思？ |
| 时机与副作用 | 注册/世界就绪/区块加载前提；是否修改世界，是否能重试，是否需要读回或保存？ |
| 权威与取消 | 身份和目标来自哪里；候选字段如何重验；取消字段是否改原始事件对象？ |
| 消费与失败路径 | 下游按什么类型消费结果；失败如何反馈、隔离或回滚，不能把 reason 当 data |
| 证据状态 | DOC_VERIFIED、HOST_TESTED、GAME_OBSERVED、CONFLICT 或 NOT_RUN，并记录实际覆盖范围 |

## 提交前逐调用复核

- 正向追踪一条实际路径：输入 → 可信事件/请求 → 验证 → API → 读回/持久化 → 响应 → UI。查明每一步的字段与形状，不能只看到函数存在。
- 覆盖空手/空槽、合法空结果、读取失败、未加载、重复事件、过期状态、部分成功和异常分支中与改动相关的样例。
- 区分引擎原生返回值与项目包装器返回值；统一包装合同后检查每个调用者，不从一种方法外推另一种方法。
- 静态校验检查调用点、字段读取、导入/成员存在与合同一致；动态对象无法证明时明确列出待测项。只检查关键词是否出现不能证明参数正确。
- 宿主模拟必须使用真实文档形状并保留失败样例。缺少游戏证据时，主机测试通过仍不登记为游戏通过。
